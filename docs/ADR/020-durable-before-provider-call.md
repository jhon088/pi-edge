# ADR 020 — Durable before the provider call

Status: accepted (milestone 6)

## Context

Every milestone so far ran one use case inside exactly one SQLite transaction:
validate, mutate, journal, commit. That shape is only possible when nothing in
the use case talks to the outside world.

A card payment does. And the dangerous ordering is obvious once stated: if we
call the provider first and persist afterwards, a process death in between
leaves a customer charged with **no local record that the charge was ever
attempted**. Nothing can reconcile what was never written.

## Decision

Every provider interaction is bracketed by two separate database transactions,
and the provider is called with **no transaction open**.

### StartPayment (card)

```
BEGIN
  validate: totalized, basket lockable, amount <= remaining balance,
            no unresolved attempt on this sale
  insert Payment(CREATED) and Attempt #n(PROCESSING) with a correlation_id
  Payment -> IN_PROGRESS ; transaction -> PAYMENT_IN_PROGRESS
  record request_id -> payment_id      (idempotency, ADR: processed_commands)
  journal PAYMENT_STARTED
COMMIT
                      <-- a crash here leaves a PROCESSING attempt: unresolved,
                          reconcilable, never assumed failed
provider.start_payment({ correlation_id, amount, tender })
                      <-- a crash here leaves the same PROCESSING attempt
BEGIN
  re-read the attempt; if already resolved, no-op (replay safe)
  persist AUTHORIZED | FAILED | UNKNOWN (+ provider_reference)
  if AUTHORIZED: commit the payment, recompute the transaction
  journal PAYMENT_AUTHORIZED / PAYMENT_COMMITTED / PAYMENT_FAILED / PAYMENT_UNKNOWN
COMMIT
```

### StartPayment (cash)

One transaction. There is no provider to call, so there is nothing to be
ambiguous about.

### ReconcilePayment

The provider call is a **query**, so nothing has to be durable beforehand: a
crash before it leaves the attempt exactly as it was. One transaction after the
query persists the resolution. The `request_id → payment_id` binding is
recorded so a replay re-resolves instead of re-querying blindly.

### ReversePayment

Durable-before-call, same as StartPayment: `REVERSAL_PENDING` is committed
first, so a reversal that reached the provider is always recorded locally.

## The correlation identity

The attempt carries a `correlation_id` generated by the core and committed
*before* the call. It is what a provider is asked about during reconciliation,
and what makes a provider-side retry idempotent. The provider's own
`provider_reference` is recorded when it comes back, and is unique per
provider so one provider operation cannot be stored under two attempts.

Four identities are kept distinct, deliberately:

| Identity | Scope | Purpose |
| --- | --- | --- |
| `request_id` | one client command | command idempotency (`processed_commands`) |
| `payment_id` | one tender of one sale | the commercial payment |
| `attempt_id` | one provider interaction | attempt history |
| `correlation_id` / `provider_reference` | the provider's view | provider-side idempotency and reconciliation |

Collapsing any two of them would make a retry either duplicate a charge or
lose history.

## Consequences

* `EdgeApplication` gains a payment-provider port as a type parameter. The
  composition root chooses the implementation; today that is always
  `SimulatorPaymentProvider`.
* A use case that calls a provider is no longer a single `transact` closure.
  The two-phase shape is explicit in `payment_service.rs` and is the only
  place in the core where it exists.
* Outbox is untouched: payment events are local journal facts. The sale still
  produces exactly one `SALE_FINALIZED` outbox event when it finalizes, which
  is the only thing upstream needs for now. Adding payment-level outbox events
  before there is a consumer for them would be speculative.
